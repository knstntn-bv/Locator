# Инструкции проекта

## Изменения структуры БД

При каждом изменении структуры БД обязательно поддерживать два SQL-представления:

1. Новую последовательную миграцию в `supabase/migrations/`, переводящую текущую структуру в желаемую. Уже применённые миграции не переписывать.
2. Единый кумулятивный файл `supabase/schema.sql`, создающий все объекты приложения с нуля в их итоговом актуальном виде. Обновлять этот файл в том же изменении, что и миграцию.

Кумулятивная схема — конечное определение структуры, а не конкатенация исторических ALTER/DROP. Включать таблицы, ограничения, индексы, функции, триггеры, расширения, права доступа и RLS-политики по мере их появления. Отмечать, до какой миграции схема актуальна, и необходимые внешние предпосылки.

`supabase/schema.sql` хранить вне каталога миграций: это альтернативный способ начального развёртывания, а не следующая миграция. Не выполнять его поверх существующей структуры и не добавлять команды удаления существующей БД.

Данные и seed хранить отдельно. Изменения только данных не требуют обновления схемы. При изменении структуры поддерживать совместимость seed с финальной схемой.

В документации различать два пути: существующая БД обновляется последовательными миграциями; новая БД создаётся либо историей миграций, либо кумулятивной схемой. Не применять оба пути к одной и той же новой структуре. При наличии инструмента учёта миграций документировать согласование его истории при развёртывании через schema.sql.
