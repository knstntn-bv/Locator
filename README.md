# Eventr — proof of concept

Минимальное приложение: карта с зумом, метки событий с попапами и фильтр по двум датам. Без регистрации, каталогов, социальных функций и редактора событий.

Стек: TypeScript + Vite, MapLibre GL JS + OpenFreeMap, Supabase PostgreSQL. Для одного экрана React пока не нужен. Отдельного сервера и PostGIS для этого POC нет: координаты хранятся в таблице, небольшой набор событий загружается по датам.

## Структура

```text
src/
  main.ts           карта, метки, попапы и фильтр
  events.ts         чтение событий из Supabase
  dates.ts          границы интервала дат
  style.css         оформление
supabase/migrations/
  001_events.sql    таблица событий и публичное чтение
  002_seed_events.sql  пять вымышленных событий
supabase/schema.sql  актуальная структура для создания с нуля
tests/              проверки интервала дат
.github/workflows/deploy.yml  публикация GitHub Pages
docs/               спецификация и архитектурные решения
```

## 1. Подключить Supabase

1. Создать проект Supabase. Auth, Storage, Realtime и Edge Functions для POC настраивать не нужно.
2. В SQL Editor последовательно выполнить содержимое `supabase/migrations/001_events.sql`, затем `002_seed_events.sql`. Первая миграция рассчитана на одно применение в новом проекте; повторный seed не дублирует события.
3. В настройках проекта найти Project URL и **publishable key** (допустим также legacy anon key). Не использовать secret key или service_role.
4. Скопировать `.env.example` в `.env.local`, указать URL и публичный ключ.

В БД создаётся только таблица `events`. Используется встроенная инфраструктурная роль Supabase `anon`: это не пользователь и не роль Eventr. RLS допускает публичное чтение событий; запись из браузера запрещена. Все данные POC публичны. Изменение данных выполняется SQL от владельца проекта.

Seed создаёт вымышленные события в Москве относительно даты применения миграции. Они не являются анонсами реальных мероприятий. Если запуск происходит существенно позже, выберите соответствующие даты в фильтре или обновите даты SQL-запросом.

## 2. Запустить локально

### Правило SQL-миграций

Каждое изменение структуры оформляется новой миграцией в `supabase/migrations/` и одновременным обновлением единого `supabase/schema.sql`. В нём хранится финальная структура, включая индексы, ограничения, права и RLS. Seed-данные в него не входят. Правило закреплено также в `AGENTS.md`.

Для нового Supabase-проекта можно вместо `001_events.sql` выполнить `supabase/schema.sql`, затем отдельно `002_seed_events.sql`. Не выполнять оба файла создания структуры в одной БД. Кумулятивный файл не удаляет существующие объекты и предназначен только для новой структуры приложения; системные объекты Supabase он не воссоздаёт.

Для существующей БД применять только ещё не применённые последовательные миграции. На текущем этапе SQL запускается вручную, без автоматического учёта истории. При развёртывании через schema.sql записать его версию: структура уже включает `001_events.sql`, поэтому эту миграцию повторно применять нельзя. При переходе на Supabase CLI потребуется отдельно согласовать историю миграций с созданной схемой.

Изменения только данных не требуют обновления кумулятивной схемы.

### Локальный запуск

Нужен Node.js 24 LTS.

```sh
npm ci
npm run dev
```

Открыть адрес, который выведет Vite. В PowerShell при запрете выполнения `npm.ps1` использовать `npm.cmd` вместо `npm`.

```sh
npm test
npm run build
npm run preview
```

Без заполненного окружения карта доступна, а приложение показывает сообщение о необходимости подключения Supabase. После изменения `.env.local` перезапустить Vite.

## 3. Карта

OpenFreeMap уже подключён стилем `https://tiles.openfreemap.org/styles/liberty`. Регистрация, ключ и оплата для публичного сервиса не нужны. Требуется интернет и поддержка WebGL в браузере. Атрибуция карты сохраняется штатным контролом MapLibre.

Карта центрируется на Москве до первой загрузки событий, затем один раз подстраивается под найденные события. При последующих изменениях дат выбранный пользователем масштаб сохраняется. Метки открывают название, описание, место и время в часовом поясе события.

## 4. GitHub Pages

1. Разместить проект в GitHub-репозитории. Workflow настроен на ветку `main`; если основная ветка другая, изменить `deploy.yml`.
2. В `Settings → Secrets and variables → Actions → Variables` создать repository variables:
   - `VITE_SUPABASE_URL`;
   - `VITE_SUPABASE_PUBLISHABLE_KEY`.
3. В `Settings → Pages → Build and deployment → Source` выбрать **GitHub Actions**.
4. Отправить изменения в `main` либо запустить workflow вручную из вкладки Actions.
5. Открыть адрес из результата deployment и проверить события.

Значения `VITE_*` входят в публичную сборку. Защита обеспечивается правами БД, а не скрытием ключа. После изменения переменных нужно заново запустить сборку. Относительный `base` позволяет публиковать приложение в подпапке репозитория; вложенных маршрутов в POC нет.

## Поведение фильтра

По умолчанию выбран период от сегодня до шестого следующего дня — семь календарных дней. Обе введённые даты включены, границы определяются в часовом поясе браузера. Время в попапе отображается в часовом поясе события, который хранится отдельно.

Событие включается, если `starts_at < конец_дня_последней_даты` и `ends_at > начало_первой_даты`. Технически верхняя граница — полночь следующего дня, не включительно. Завершившееся ровно в начале выбранного периода событие не показывается. Фильтр обновляется после изменения поля, кнопка применения не нужна.

## Проверка после подключения

- В исходном интервале видны четыре тестовых события; пятое находится через две недели после применения seed.
- Клик по метке открывает попап, зум работает.
- Выбор дня внутри «Выставки на неделю» сохраняет её на карте.
- Интервал без событий показывает пустую карту и соответствующее сообщение.
- Обратный интервал показывает ошибку и убирает прежние метки.
- Публичный ключ позволяет читать `events`, но не добавлять, менять и удалять записи.

## Ограничения POC

Нет кластеризации, поиска адресов, создания событий, авторизации, обложек, уведомлений, подписок и автоподгрузки по области карты. Для небольшого тестового набора используются отдельные DOM-маркеры; при росте объёма потребуется слой GeoJSON с кластеризацией. Публичный OpenFreeMap не предоставляет SLA.
